# Week 3 Project — Tasks REST API

A REST API built with Node.js, Express, and MongoDB (via Mongoose). It exposes
full CRUD endpoints for two collections — `tasks` and `categories` (a task
optionally belongs to a category) — with schema validation, centralized error
handling, and GitHub OAuth login that restricts write access.

## Requirements

- Node.js 18+
- npm
- A MongoDB database (MongoDB Atlas cluster or local `mongod` instance)
- A GitHub OAuth App (see [Authentication](#authentication-github-oauth) below)

## Setup

```bash
npm install
cp .env.example .env
```

Edit `.env` and set `MONGODB_URI` to your connection string, e.g.:

```
MONGODB_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/<database>
```

`.env` is listed in `.gitignore` and must never be committed.

If the server fails locally with `querySrv ECONNREFUSED`, your router's DNS is
rejecting the SRV lookup for `mongodb+srv://` URIs. Add this line to your local
`.env` (not needed on Render):

```
DNS_SERVERS=8.8.8.8,1.1.1.1
```

You also need `SESSION_SECRET`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, and
`GITHUB_CALLBACK_URL` set before the server will start — see the next section.

## Running

```bash
npm run dev    # starts with nodemon (auto-reload)
npm start      # starts in normal mode
```

The server connects to MongoDB on startup and exits if the connection fails.
It then listens on `http://localhost:3000` by default (configurable via `PORT`).

## Authentication (GitHub OAuth)

Login is handled with [Passport.js](http://www.passportjs.org/) and the GitHub
OAuth strategy. Sessions are stored server-side in MongoDB (via
`connect-mongo`) and tracked with a signed, `httpOnly` session cookie —
there is no local username/password form, so **no passwords are ever stored**
and bcrypt isn't needed here (there's nothing to hash; GitHub verifies the
user's credentials on its own consent screen).

### 1. Create a GitHub OAuth App

At <https://github.com/settings/developers> → **New OAuth App**, register one
app for this project. GitHub OAuth Apps now accept multiple redirect URIs, so
add both of these (click **Add redirect URI** for the second one) rather than
making a separate app per environment:

- `http://localhost:3000/auth/github/callback` (local dev)
- `https://week3-project-b5y1.onrender.com/auth/github/callback` (Render)

Homepage URL can be either one (e.g. the Render URL, or `http://localhost:3000`
while you're still testing locally) — it's just informational text shown on
GitHub's consent screen, and isn't validated against the actual request.

After registering, copy the **Client ID**, then click "Generate a new client
secret" and copy the **Client Secret** (GitHub only shows it once).

### 2. Set the environment variables

Local `.env`:

```
SESSION_SECRET=<any long random string>
GITHUB_CLIENT_ID=<client id>
GITHUB_CLIENT_SECRET=<client secret>
GITHUB_CALLBACK_URL=http://localhost:3000/auth/github/callback
```

Generate a `SESSION_SECRET` with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

On Render, set the same four variables under **Environment**, reusing the same
Client ID/Secret but with `GITHUB_CALLBACK_URL` pointed at the Render URL, plus
`NODE_ENV=production` (marks the session cookie `Secure`, i.e. HTTPS-only).

### 3. Try it out

- Log in: open `/auth/github` in a **browser tab** (not Swagger's "Try it out" —
  it can't follow the multi-site OAuth redirect chain). Approve the app on
  GitHub; you're redirected to `/auth/profile`, which shows your account
  (created automatically on first login) as JSON.
- Check status without logging in: `GET /auth/status` → `{ "loggedIn": false }`.
- View a restricted route: `GET /auth/profile` returns `401` if you're not
  logged in, and your account info if you are.
- Log out: open `/auth/logout`.
- Restricted task routes: `POST /tasks`, `PUT /tasks/:id`, and `DELETE /tasks/:id`
  all require login and return `401` otherwise; `GET /tasks` and `GET /tasks/:id`
  stay public. Because Swagger UI is served from the same origin as the API, once
  you've logged in via a browser tab, `/api-docs` → **Try it out** sends the same
  session cookie automatically, so you can exercise the protected routes there too.

## Data model

`User` documents (`src/models/user.model.js`) — created automatically on first
GitHub login, never via a public signup endpoint:

| Field         | Type   | Rules                                  |
|---------------|--------|------------------------------------------|
| `_id`         | ObjectId | generated by MongoDB                    |
| `githubId`    | String | required, unique                          |
| `username`    | String | required (GitHub login)                   |
| `displayName` | String | GitHub display name, defaults to username |
| `email`       | String | from GitHub, may be `null`                |
| `avatarUrl`   | String | GitHub avatar, may be `null`               |
| `createdAt`   | Date   | set automatically                          |
| `updatedAt`   | Date   | set automatically                          |

`Task` documents (`src/models/task.model.js`):

| Field       | Type    | Rules                                        |
|-------------|---------|-----------------------------------------------|
| `_id`       | ObjectId | generated by MongoDB                          |
| `title`     | String  | required, trimmed, 1–200 characters            |
| `done`      | Boolean | defaults to `false`                            |
| `category`  | ObjectId | optional, references a `Category` (`ref: 'Category'`); `null` if unset |
| `createdAt` | Date    | set automatically                              |
| `updatedAt` | Date    | set automatically                              |

`Category` documents (`src/models/category.model.js`) — a second, independent
collection used to group tasks:

| Field         | Type   | Rules                                    |
|---------------|--------|--------------------------------------------|
| `_id`         | ObjectId | generated by MongoDB                      |
| `name`        | String | required, trimmed, 1–50 characters, **unique** |
| `description` | String | optional, up to 300 characters, defaults to `''` |
| `createdAt`   | Date   | set automatically                          |
| `updatedAt`   | Date   | set automatically                          |

`GET /tasks` and `GET /tasks/:id` populate `category` with the referenced
document (`name` and `description` only) instead of returning the raw id.

## Interactive documentation and testing (Swagger)

Swagger UI is served by the API itself:

- Local: http://localhost:3000/api-docs
- Raw OpenAPI spec: `/api-docs.json`

Open `/api-docs`, expand a route, click **Try it out**, fill in the parameters or
body, and press **Execute** to send a real request and see the response. A full
test flow: `POST /categories` → copy the returned `_id` → `POST /tasks` with
that id as `category` → `GET /tasks/{id}` (see the populated category) →
`PUT /tasks/{id}` → `DELETE /tasks/{id}` → `GET /tasks/{id}` (404). The spec
lives in `src/docs/openapi.js`.

## Endpoints

### API root

**GET** `/`

Response `200`:

```json
{
  "message": "Tasks API is running",
  "health": "/health",
  "docs": "/api-docs",
  "tasks": "/tasks",
  "auth": { "loggedIn": false, "user": null, "login": "/auth/github", "profile": "/auth/profile" }
}
```

### Health check

**GET** `/health`

Response `200`:

```json
{ "status": "ok" }
```

### Log in with GitHub

**GET** `/auth/github`

Open in a browser tab. Redirects to GitHub's consent screen; approving it
redirects back to `/auth/github/callback`, which creates/updates the local
account and redirects to `/auth/profile`.

### Log out

**GET** `/auth/logout`

Destroys the session. Response `200`:

```json
{ "message": "Logged out successfully" }
```

### Check login status

**GET** `/auth/status` — public.

Response `200`:

```json
{ "loggedIn": true, "username": "octocat" }
```

### Get account info (restricted)

**GET** `/auth/profile` — requires login.

Response `200`: the logged-in user's document.

Response `401` if not logged in:

```json
{ "error": "You must be logged in to do that. Go to /auth/github to log in." }
```

### List tasks

**GET** `/tasks`

Response `200`:

```json
[
  { "_id": "651f...", "title": "Learn Express", "done": false, "createdAt": "...", "updatedAt": "..." }
]
```

### Get a task by id

**GET** `/tasks/:id`

Response `200`: the task document.

Response `404` if no task has that id:

```json
{ "error": "Task not found" }
```

Response `400` if `:id` is not a valid MongoDB ObjectId:

```json
{ "error": "Invalid id: <value>" }
```

### Create a task (restricted)

**POST** `/tasks` — requires login.

Request body:

```json
{ "title": "Write documentation", "done": false, "category": "651f1f1f1f1f1f1f1f1f1f1e" }
```

`title` is required (validated by the schema). `done` defaults to `false` if omitted.
`category` is optional — the `_id` of an existing category (see `GET /categories`).

Response `201`: the created task document.

Response `400` if validation fails (e.g. missing/empty `title`, or `title` over 200 characters):

```json
{ "error": "title is required" }
```

Response `401` if not logged in.

### Update a task (restricted)

**PUT** `/tasks/:id` — requires login.

Request body (any subset of these fields):

```json
{ "title": "Updated title", "done": true }
```

Response `200`: the updated task document.

Response `404` if the task does not exist.

Response `400` if validation fails or `:id` is not a valid ObjectId.

Response `401` if not logged in.

### Delete a task (restricted)

**DELETE** `/tasks/:id` — requires login.

Response `204` (no body) on success.

Response `404` if the task does not exist.

Response `400` if `:id` is not a valid ObjectId.

Response `401` if not logged in.

### List categories

**GET** `/categories`

Response `200`:

```json
[{ "_id": "651f...", "name": "Work", "description": "Job-related tasks", "createdAt": "...", "updatedAt": "..." }]
```

### Get a category by id

**GET** `/categories/:id`

Response `200`: the category document.

Response `404` if no category has that id. Response `400` if `:id` is not a valid ObjectId.

### Create a category (restricted)

**POST** `/categories` — requires login.

Request body:

```json
{ "name": "Work", "description": "Job-related tasks" }
```

`name` is required, 1–50 characters, and must be unique. `description` is optional (up to 300 characters).

Response `201`: the created category document.

Response `400` if validation fails or the name is already taken:

```json
{ "error": "name 'Work' already exists" }
```

Response `401` if not logged in.

### Update a category (restricted)

**PUT** `/categories/:id` — requires login.

Request body (any subset of `name` and `description`).

Response `200`: the updated category document.

Response `404` if the category does not exist. Response `400` if validation fails, the name
is already taken, or `:id` is not a valid ObjectId. Response `401` if not logged in.

### Delete a category (restricted)

**DELETE** `/categories/:id` — requires login.

Response `204` (no body) on success. Deleting a category does not touch tasks that
reference it — they keep the now-dangling `category` id.

Response `404` if the category does not exist. Response `400` if `:id` is not a valid
ObjectId. Response `401` if not logged in.

### Unmatched routes

Any request to a route that doesn't exist returns `404`:

```json
{ "error": "Route not found: GET /nope" }
```

## Validation

Handled at the Mongoose schema level, one collection per model file:

`Task` (`src/models/task.model.js`):
- `title` must be present, non-empty after trimming, and at most 200 characters.
- `done` must be a boolean if provided.
- `category`, if provided, must be a valid ObjectId (existence isn't enforced — see
  "Delete a category" above).

`Category` (`src/models/category.model.js`):
- `name` must be present, non-empty after trimming, at most 50 characters, and unique
  across the collection.
- `description`, if provided, must be at most 300 characters.

Both `findByIdAndUpdate` calls run with `runValidators: true` so updates are validated
the same way as creates.

## Error handling

Centralized in `src/middleware/errorHandler.js`, registered last in `app.js`. It's
shared by both the `tasks` and `categories` controllers — every database call in both
is wrapped in `try/catch` and forwards to this middleware via `next(err)`:

- **`ValidationError`** (failed schema validation, either collection) → `400` with the
  validation message(s).
- **`CastError`** (malformed ObjectId in `:id`, or a wrong type such as `"done": "maybe"`) → `400`
  with a message like `Invalid id: abc` or `Invalid value for 'done': maybe`.
- **Duplicate key (`E11000`)** (e.g. a `Category.name` that already exists) → `400` with
  a message like `name 'Work' already exists`.
- **Malformed JSON body** → `400 { "error": "Invalid JSON in request body" }`.
- **Not logged in** on a restricted route (`ensureAuthenticated`, `src/middleware/auth.js`) →
  `401 { "error": "You must be logged in to do that. Go to /auth/github to log in." }`.
- **Unmatched routes** → `404` via the `notFound` middleware.
- **Anything else** → logged to the console and returned as `500 { "error": "Internal server error" }`.

## Example requests (curl)

GitHub's OAuth consent screen requires a real browser, so log in at `/auth/github`
first, then copy the `connect.sid` cookie (DevTools → Application → Cookies) to
use curl for the restricted routes — or just use Swagger UI, which reuses your
browser session automatically.

```bash
# List tasks (public)
curl http://localhost:3000/tasks

# Get one task (public)
curl http://localhost:3000/tasks/<id>

# Create a task (requires the session cookie from a browser login)
curl -X POST http://localhost:3000/tasks \
  -H "Content-Type: application/json" \
  -H "Cookie: connect.sid=<value from browser>" \
  -d '{"title":"Write documentation"}'

# Update a task
curl -X PUT http://localhost:3000/tasks/<id> \
  -H "Content-Type: application/json" \
  -H "Cookie: connect.sid=<value from browser>" \
  -d '{"done":true}'

# Delete a task
curl -X DELETE http://localhost:3000/tasks/<id> \
  -H "Cookie: connect.sid=<value from browser>"

# Create a category
curl -X POST http://localhost:3000/categories \
  -H "Content-Type: application/json" \
  -H "Cookie: connect.sid=<value from browser>" \
  -d '{"name":"Work","description":"Job-related tasks"}'
```

## Verifying in MongoDB

After exercising the endpoints above, confirm the changes landed in the database:

1. Open your cluster in **MongoDB Atlas** (Browse Collections) or connect with
   **MongoDB Compass** / `mongosh` using the same `MONGODB_URI`.
2. After a `POST /tasks` or `POST /categories`, the new document should appear in the
   `tasks` or `categories` collection, respectively.
3. After a `PUT /tasks/:id` or `PUT /categories/:id`, the document's fields (and
   `updatedAt`) should reflect the update.
4. After a `DELETE`, the document should no longer be in its collection.
5. Because data is persisted (not in-memory), documents survive a server restart —
   restarting and re-running `GET /tasks` / `GET /categories` should still show
   previously created data.

## Deploying to Render

1. Push the repo to GitHub.
2. In Render, create a new **Web Service** and connect the repository.
3. Settings: Build Command `npm install`, Start Command `npm start`.
4. Under **Environment**, add these config vars:
   - `MONGODB_URI` — same value as your local `.env`.
   - `SESSION_SECRET` — a different long random string than your local one.
   - `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` — same values as local (one OAuth
     App, see [Authentication](#authentication-github-oauth)).
   - `GITHUB_CALLBACK_URL` — `https://<your-render-subdomain>.onrender.com/auth/github/callback`.
   - `NODE_ENV` — `production` (marks the session cookie `Secure`/HTTPS-only).
   - Do not set `PORT` — Render provides it.
5. In MongoDB Atlas → Network Access, allow connections from Render
   (e.g. `0.0.0.0/0`), otherwise the service cannot reach the cluster.
6. In the GitHub OAuth App's settings, make sure this exact Render callback URL
   is listed under **Redirect URIs** (Render assigns the subdomain when the
   service is first created, so double-check it once you know the real URL).

Live API: https://week3-project-b5y1.onrender.com — Swagger UI at https://week3-project-b5y1.onrender.com/api-docs

## Project structure

```
src/
├── index.js                    # entry point: connects to MongoDB, then starts the server
├── app.js                      # Express app config: sessions, passport, routes, error handling
├── config/
│   ├── db.js                   # Mongoose connection
│   └── passport.js             # GitHub OAuth strategy + session serialize/deserialize
├── docs/
│   └── openapi.js              # OpenAPI 3 spec served by Swagger UI at /api-docs
├── models/
│   ├── task.model.js           # Task schema/model + validation rules (optional category ref)
│   ├── category.model.js       # Category schema/model + validation rules (unique name)
│   └── user.model.js           # User schema (created on first GitHub login)
├── routes/
│   ├── index.routes.js         # root + health check routes
│   ├── auth.routes.js          # GitHub login/callback/logout/status/profile routes
│   ├── tasks.routes.js         # tasks CRUD routes (writes require login)
│   └── categories.routes.js    # categories CRUD routes (writes require login)
├── controllers/
│   ├── index.controller.js
│   ├── auth.controller.js      # login callback, logout, profile, status logic
│   ├── tasks.controller.js     # tasks CRUD logic (MongoDB via Mongoose)
│   └── categories.controller.js # categories CRUD logic (MongoDB via Mongoose)
└── middleware/
    ├── errorHandler.js         # 404 handler + centralized error handler
    └── auth.js                 # ensureAuthenticated route guard (401 if not logged in)
```

## Notes

Data is persisted in MongoDB. The previous in-memory numeric `id` field was
replaced by MongoDB's `_id` (ObjectId) as part of this migration. User accounts
are created automatically on first GitHub login; there is no local signup form
and no password of any kind is ever stored.
