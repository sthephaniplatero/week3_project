# Week 3 Project — Tasks REST API

A REST API built with Node.js, Express, and MongoDB (via Mongoose). It exposes
full CRUD endpoints for managing a `tasks` collection, with schema validation
and centralized error handling.

## Requirements

- Node.js 18+
- npm
- A MongoDB database (MongoDB Atlas cluster or local `mongod` instance)

## Setup

```bash
npm install
cp .env.example .env
```

Edit `.env` and set `MONGODB_URI` to your connection string, e.g.:

```
MONGODB_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/<database>
```

## Running

```bash
npm run dev    # starts with nodemon (auto-reload)
npm start      # starts in normal mode
```

The server connects to MongoDB on startup and exits if the connection fails.
It then listens on `http://localhost:3000` by default (configurable via `PORT`).

## Data model

`Task` documents (`src/models/task.model.js`):

| Field       | Type    | Rules                                      |
|-------------|---------|---------------------------------------------|
| `_id`       | ObjectId | generated by MongoDB                       |
| `title`     | String  | required, trimmed, 1–200 characters         |
| `done`      | Boolean | defaults to `false`                         |
| `createdAt` | Date    | set automatically                           |
| `updatedAt` | Date    | set automatically                           |

## Endpoints

### Health check

**GET** `/health`

Response `200`:

```json
{ "status": "ok" }
```

### List tasks

**GET** `/tasks`

Response `200`:

```json
[
  { "_id": "651f...", "title": "Learn Express", "done": false, "createdAt": "...", "updatedAt": "..." }
]
```

### Get a task by id

**GET** `/tasks/:id`

Response `200`: the task document.

Response `404` if no task has that id:

```json
{ "error": "Task not found" }
```

Response `400` if `:id` is not a valid MongoDB ObjectId:

```json
{ "error": "Invalid id: <value>" }
```

### Create a task

**POST** `/tasks`

Request body:

```json
{ "title": "Write documentation", "done": false }
```

`title` is required (validated by the schema). `done` defaults to `false` if omitted.

Response `201`: the created task document.

Response `400` if validation fails (e.g. missing/empty `title`, or `title` over 200 characters):

```json
{ "error": "title is required" }
```

### Update a task

**PUT** `/tasks/:id`

Request body (any subset of these fields):

```json
{ "title": "Updated title", "done": true }
```

Response `200`: the updated task document.

Response `404` if the task does not exist.

Response `400` if validation fails or `:id` is not a valid ObjectId.

### Delete a task

**DELETE** `/tasks/:id`

Response `204` (no body) on success.

Response `404` if the task does not exist.

Response `400` if `:id` is not a valid ObjectId.

### Unmatched routes

Any request to a route that doesn't exist returns `404`:

```json
{ "error": "Route not found: GET /nope" }
```

## Validation

Handled at the Mongoose schema level (`src/models/task.model.js`):

- `title` must be present, non-empty after trimming, and at most 200 characters.
- `done` must be a boolean if provided.

`findByIdAndUpdate` runs with `runValidators: true` so updates are validated the
same way as creates.

## Error handling

Centralized in `src/middleware/errorHandler.js`, registered last in `app.js`:

- **`ValidationError`** (failed schema validation) → `400` with the validation message(s).
- **`CastError`** (malformed ObjectId in `:id`) → `400` with the invalid value.
- **Unmatched routes** → `404` via the `notFound` middleware.
- **Anything else** → logged to the console and returned as `500 { "error": "Internal server error" }`.

Every controller uses `try/catch` and forwards errors to this middleware via `next(err)`.

## Example requests (curl)

```bash
# List tasks
curl http://localhost:3000/tasks

# Create a task
curl -X POST http://localhost:3000/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"Write documentation"}'

# Get one task
curl http://localhost:3000/tasks/<id>

# Update a task
curl -X PUT http://localhost:3000/tasks/<id> \
  -H "Content-Type: application/json" \
  -d '{"done":true}'

# Delete a task
curl -X DELETE http://localhost:3000/tasks/<id>
```

## Verifying in MongoDB

After exercising the endpoints above, confirm the changes landed in the database:

1. Open your cluster in **MongoDB Atlas** (Browse Collections) or connect with
   **MongoDB Compass** / `mongosh` using the same `MONGODB_URI`.
2. After a `POST /tasks`, the new document should appear in the `tasks` collection.
3. After a `PUT /tasks/:id`, the document's fields (and `updatedAt`) should reflect the update.
4. After a `DELETE /tasks/:id`, the document should no longer be in the collection.
5. Because data is persisted (not in-memory), tasks survive a server restart —
   restarting and re-running `GET /tasks` should still show previously created tasks.

## Project structure

```
src/
├── index.js                    # entry point: connects to MongoDB, then starts the server
├── app.js                      # Express app configuration, error handling wiring
├── config/
│   └── db.js                   # Mongoose connection
├── models/
│   └── task.model.js           # Task schema/model + validation rules
├── routes/
│   ├── index.routes.js         # health check route
│   └── tasks.routes.js         # tasks CRUD routes
├── controllers/
│   ├── index.controller.js
│   └── tasks.controller.js     # tasks CRUD logic (MongoDB via Mongoose)
└── middleware/
    └── errorHandler.js         # 404 handler + centralized error handler
```

## Notes

Data is persisted in MongoDB. The previous in-memory numeric `id` field was
replaced by MongoDB's `_id` (ObjectId) as part of this migration.
